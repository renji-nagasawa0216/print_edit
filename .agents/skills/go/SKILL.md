# 開発フロー

1. 依頼範囲、対象の作業ディレクトリ、既存差分、参照資料、完了条件を確認する。指定された工程から始める場合は、前工程の成果物と現状が一致するか確認する。
2. 下表の順に実行する。既存の成果物が要件を満たす工程は再利用する。画面変更がないときは画面案を省略できる。小さな修正では要件・仕様・テストケースを会話内の短いメモにまとめてよい。
3. 未確定の仕様が結果に影響するときは、根拠、選択肢、推奨案をまとめて判断を求める。テストの再実行や、要件から修正方法を特定できる実装不具合の修正は依頼範囲内で続ける。
4. 実装の失敗は実装工程へ戻す。期待結果の誤りが疑われた場合は要件と判定根拠に戻る。原因が同じ失敗を2回繰り返した場合は、試行と残る阻害要因を報告する。
5. 最後に変更点、実行した検証と結果、未検証の範囲を報告する。コミットや外部公開を含む依頼では、該当する操作の明示的な依頼を確認してから進める。

| 工程 | 参照するスキル | 次へ渡す内容 |
| --- | --- | --- |
| 要件 | `$rd` | 要件、判断済み事項、完了条件 |
| 画面案 | `$mk` | 構成、主要状態、画面幅ごとの挙動 |
| 仕様・テストケース | `$st` | 要件と期待結果を対応づけた仕様 |
| 実装 | `$im` | 変更箇所、実装時の判断 |
| 検証 | `$vf` | ケース別結果と証跡 |
| 差分レビュー | `$sr` | 指摘、根拠、残るリスク |
| 公開 | `$ship` | コミットID、公開先、PR URL |

## 状態・計測・再開

- リポジトリのルートから `python3 .codex/hooks/harness.py status` を実行する。中断した作業を再開する依頼では、保存された工程と現在のブランチ・差分・承認済みの要件を照合する。
- 工程の開始時に `python3 .codex/hooks/harness.py stage <工程> running`、終了時に `stage <工程> passed|failed|skipped` を実行する。判断が必要になった場合は `stage <工程> waiting '<再開に必要な情報>'`、回答後は `running` を記録する。情報には認証情報を入れない。中止時は `cancelled` を記録する。時刻と直前イベントからの間隔は `metrics` で確認する。
- 明示的に自動継続を依頼され、未完了のローカル作業が残る場合は `harness.py continue <現在のセッションID>` で継続を一度予約できる。この場合だけ応答の最終行を `[harness:continue]` とする。判断待ちや外部操作の前には予約しない。
